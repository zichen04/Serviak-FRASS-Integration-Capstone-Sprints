## Agenda and purpose

Continue the technical orientation with Dr. Crookston. The team sought to understand the FVS software already on Serviak, how FVS Online and R can construct runs, and what user-specific workflows the FRASS integration may need. The meeting was a walkthrough and discussion rather than a session in which tasks were assigned on the spot.

## Key discussion points

### Installation and current environment

- Previous team installed the complete Forest Service FVS package on Serviak. The team was advised to install the complete package locally as well, so members can inspect its application and settings. The installation and versions still need to be verified.
- Update from Dr. Crookston with a link to the complete FVS package. They describe using the Forest Service installation as the source of binaries so future updates are easier to manage. Verify the exact package, version, and location before writing setup instructions.
- FVS Online can be started through R.  `require(fvsOL)` to load the package and `fvsOL()` to start its local browser interface; the location of the FVS binaries must be configured or discovered. This was a demonstration of the software, not proof that the team has installed it locally.
- Serviak users have individual workspaces or working directories. Automating an FVS Online workspace per user. A workspace may contain input/output/project databases, R scripts, and a project ID, and may be accessible through both command-line functions and the GUI. The exact ownership and isolation model still needs to be defined.

### User data and run construction

- A possible workflow discussed was: begin with FRASS data, let a user modify their copy, accept the modified data back, retain both the original and modified versions, and construct runs from the chosen version.
- Users may already have FVS data on their own computers. The system may need an import path for user-supplied data in addition to data generated from FRASS.
- R functions exposed by FVS Online for constructing and starting runs without using the GUI. They refer to a run UUID, cases for individual stands, and a case UUID. Re-running a baseline can produce different IDs; the team should confirm which IDs FRASS must retain to distinguish repeated runs from the same stand.
- Runs are described as being created in the current working directory. The longer-term workflow discussed includes downloading `.db` files to a local machine, working with them there, and sending results back to Serviak. This was a proposed workflow, not an approved upload or synchronization design.
- Dr. Schlosser recommended the test data bundled with the software as a starting point for evaluation.
- The team needs to understand where further analytical needs arise before adding new flows. Did not define acceptance criteria for these paths yet.

### Results and reporting

- Need for reports from FVS output. Which reports, formats, fields, audiences, and validation rules are required remains open.
- The team should determine how results and their source data remain distinguishable when users modify inputs and create multiple runs.
- FVS output was described as SQLite tables whose data can feed later FRASS analysis, including the Flex Taper financial model. Tree-line numbers can vary between years; the team should clarify exactly which identifiers are stable before designing traceability or report joins.
